# 사이드 장기 대화와 컨텍스트 예산

2026-09-11 수정. 원래 구현은 요청 JSON 의 글자 수를 그대로 token 으로 간주하고 메인 작업의 32K 출력 예약을 상속했기 때문에, HTML, JS, 도구 결과가 많으면 정상적인 사이드 질문을 미리 거부했다.

## 오픈 소스 구현 대조

- [Grok CLI 사이드 컨텍스트](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/agent.ts#L739): 최근 사용자, 어시스턴트 텍스트에서 조각을 발췌하며, 글자 예산은 약 2000, 항목마다 최대 400자까지 잘라낸다. 이 경로에서 연속된 사이드 질의응답 이력을 유지하지 않는다.
- [Grok CLI 독립 요청](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/utils/side-question.ts): 독립 취소 신호. 모델이 지원하면 출력 상한은 2048 tokens. 도구를 제공하지 않는다.
- [Grok CLI 메인 대화 압축](https://github.com/superagent-ai/grok-cli/blob/fb97af83f06dca873281d60168430f06c8de6324/src/agent/compaction.ts): token 을 추정하고, 최근 내용을 유지하며, 새 내용을 기존 요약에 갱신해 넣고, 턴을 넘는 잘림을 처리한다.
- [OpenCode 대화 압축](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/compaction.ts): 전체 요청 추정, 출력/버퍼 예약, 최근 내용 + 롤링 요약, 도구 없는 요약 요청. 이 구현의 기본 최근 예산은 8000, 요약 출력 상한은 4096 tokens 다.
- [OpenCode 오버플로 복구](https://github.com/anomalyco/opencode/blob/b3f1a96c6dd7adeb28b36dd11add1998fc84d67b/packages/core/src/session/runner/llm.ts): 아직 어시스턴트 출력을 시작하지 않았을 때만 오버플로 복구를 시도하며, 복구 후의 호출은 같은 오버플로 복구 경로에 다시 들어가지 않는다.

ARTEX 는 독립 출력 예산, 최근 내용과 롤링 요약, 제한적 복구 방식을 참고한다. norma v0.3.6 의 구조화된 메시지와 도구 짝짓기를 유지하며, Grok 의 텍스트 발췌를 그대로 가져오지 않고, OpenCode 의 메인 대화 압축 이벤트를 ARTEX 메인 transcript 에 쓰지 않는다.

## 요청 예산과 실행

- 메시지는 norma 의 내용 블록 UTF-8 바이트 추정과 4/3 여유를 따른다. 여기에 시스템 프롬프트, 도구 schema, 메시지 포장 오버헤드를 추가로 계산한다. 추정은 모델의 정확한 token 계수가 아니다.
- 사이드 출력은 기본 최대 8192 tokens 이며, 메인 설정에 이미 설정된 출력 상한도 넘지 않는다. 서비스 환경 변수 `ARTEX_BTW_MAX_OUTPUT_TOKENS` 로 256–32768 의 상한을 설정할 수 있다. 제품 기본 모델이나 메인 작업 파라미터는 수정하지 않는다.
- 입력 예산은 컨텍스트 창에서 출력 상한과 안전 여유를 뺀 값이다. 창을 알 수 없으면 플랫폼 기본 200K 를 쓴다. 안전 여유는 창의 5% 이며 최소 128, 최대 8192 tokens 다.
- 성공한 질의응답은 증가하는 순번에 따라 배치당 최대 20개씩 로드한다. 원문은 최대 20개를 유지하며, 그 token 예산은 입력 예산의 1/4 이하이고 16K 를 넘지 않는다.
- 초과한 질의응답은 롤링 요약에 갱신한다. 요약에는 이력 출처와 컨텍스트 시각이 붙는다. 과거 어시스턴트 답변은 새 도구 증거와 같지 않으며, 충돌할 때는 최신 메인 스냅샷을 우선한다.
- 메인 컨텍스트가 여전히 너무 길면 요약본의 오래된 메시지만 요약하고 최근 것은 최대 8K tokens 를 유지한다. 잘라내는 지점은 도구 호출과 결과를 떼어 놓지 않는다. 너무 큰 단일 그룹은 통째로 요약에 들어간다.
- 요약 입력은 실제 남은 창에 따라 UTF-8 안전 분할을 하며 출력 상한은 2048 tokens 다. 빈 요약, 잘림, 도구 호출, 요약 예산 초과는 모두 캐시에 쓰지 않는다. 한 번의 사이드 요청에 요약 호출은 최대 12 회이며 같은 120 초 시간 초과의 제한을 받는다. 상한에 도달하면 명확히 실패하며 무한 루프에 빠지지 않는다.
- 모델이 처음으로 컨텍스트 초과를 반환했고 아직 텍스트나 도구 호출을 출력하지 않았다면, 더 줄인 뒤 최대 한 번 재시도한다. 추정 크기가 줄지 않으면 즉시 복구를 멈춘다. 다른 모델 오류나 부분 스트림 출력은 이 복구를 트리거하지 않는다.
- 요약, 실패한 시도, 취소 시의 사용량을 포함해 얻은 모든 사용량을 같은 사이드 요청에 누적한다. Provider 가 사용량을 반환하지 않으면 0 만 기록할 수 있을 뿐, 추정을 실제 사용량으로 위장할 수 없다.

## 영속화와 UI

`side_question_sessions.memory` 는 이전 질의응답 요약, 덮어쓴 ordinal, 스냅샷 신원별로 캐시한 메인 컨텍스트 요약을 저장한다. `side_question_requests.context_info` 는 준비 단계, 실제 재생한 그룹 수, 요약 사용 상황, 예산 추정을 저장한다.

요약은 원래 요청이 여전히 실행 중이고 정리 버전이 일치할 때만 저장한다. 비우면 캐시도 함께 지우며, 늦게 온 쓰기는 이미 정리된 데이터를 복원하지 않는다. 새 스냅샷은 이전 스냅샷 요약을 재사용하지 않는다. 요약 필드는 v3 작업 보관과 함께 저장된다. 이전 v3 에서 빠진 필드를 복원할 때는 빈 객체로 채우며, v1/v2 는 계속 호환된다.

POST 는 먼저 요청을 받아들여 반환하고, 준비와 압축은 백그라운드에서 실행하며 준입 잠금이나 데이터베이스 트랜잭션을 쥐지 않는다. SSE/이력은 준비, 질의응답 정리, 압축 복사, 답변 단계를 표시한다. 압축 실패는 그 사이드 요청의 실패 최종 상태로 저장한다. 프론트엔드는 오류를 유지하고 이번에 실패한 질문의 초안을 복원하며, 떠 있는 알림으로 입력창을 가리지 않는다. 이력 폴링은 더 이상 제출 오류를 지우지 않는다.
